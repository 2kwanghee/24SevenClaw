## 목표
관측 화면(관측 C)이 소비할 읽기 전용 집계 API 4종(`summary`/`usage`/`runs`/`seats`)을 `clickeye-api`에 신규 라우터로 추가하고 contracts를 동기화한다.

## 가정 (Assumptions)
- 신규 라우터 인증은 기존 admin 전용 관측 엔드포인트(`llm_ledger.py`, `pipeline_runs.py`)와 동일하게 `require_permission("settings:manage")` 사용 (governance-token 방식은 CE-387 스냅샷 인제스트 전용, 화면 조회에는 부적합) — 가장 보수적 선택.
- "인테이크 깔때기 pending_review/accepted/rejected"는 `tickets` 테이블이 아니라 `intake_requests.status`를 가리킨다 (실제로 이 도메인 값을 갖는 컬럼은 `intake_requests.status`뿐). `tickets_status` 필드도 `intake_requests.tickets_status`(`none|issued`)를 그대로 사용.
- 페이지네이션은 티켓이 지정한 "기존 `utils/pagination.py` 규약"을 문자 그대로 따르되, 실제 형제 엔드포인트(`llm_ledger.py`, `pipeline_runs.py`, `seat_quota.py`)는 `Page`/`paginate()` 유틸을 쓰지 않고 수동 `limit`/`offset` `Query()` + `items`/`total` 응답을 쓴다. **일관성을 위해 형제 엔드포인트 패턴(수동 limit/offset)을 따른다** — `pagination.py`의 `Page`/`paginate()`는 이 관측 라우터 시리즈에서 실제로 채택되지 않은 유틸이므로.
- `runs`/`runs/{issue_key}`는 `pipeline_runs.py`의 기존 `PipelineRunService.list_runs`(run_id 그룹핑 로직)를 재사용/확장하고 새 서비스로 중복 구현하지 않는다.
- `seats`는 CE-387의 `SeatQuotaService.latest()`를 재사용하고, 그 결과를 화면 계약 형태(계정별 최신 + 시트 상태 조인 + 24h 소비 합)로 감싸는 새 서비스 메서드/스키마만 추가한다 — `latest()` 자체의 내부 쿼리는 변경하지 않는다.
- "최근 N일"/"드릴다운" 등 숫자 파라미터 미명시 항목은 형제 엔드포인트의 기존 `limit`/`offset` 기본값·범위(`ge=1,le=...`) 관례를 그대로 따른다.

## 대상 파일
- `clickeye-api/app/api/v1/observability.py` — 신규. 4개 GET 엔드포인트 정의.
- `clickeye-api/app/api/v1/router.py` — 기존. import + `include_router` 라인 추가.
- `clickeye-api/app/services/observability_service.py` — 신규. `summary`/`usage` 집계 쿼리 (runs/seats는 기존 서비스 재사용/래핑).
- `clickeye-api/app/schemas/observability.py` — 신규. 4개 응답 스키마 (`ObservabilitySummaryResponse`, `UsagePivotResponse`, 기존 `PipelineRunListResponse`/`PipelineRunDetailResponse` 재노출 또는 참조, `SeatObservabilityResponse`).
- `clickeye-api/app/services/pipeline_run_service.py` — 기존, 재사용만 (변경 없음 또는 최소 파라미터 확장이 불가피할 때만 국소 수정).
- `clickeye-api/app/services/seat_quota_service.py` — 기존 `latest()` 재사용, 화면 계약용 신규 메서드(예: `screen_view()`) 추가.
- `clickeye-api/tests/test_observability.py` — 신규. 4개 엔드포인트 × ≥3개(성공/인증실패/유효성실패) 테스트.
- `clickeye-contracts/openapi/openapi.json`, `clickeye-contracts/generated/typescript/{types.gen.ts,sdk.gen.ts}` — `export_openapi.py` + `@hey-api/openapi-ts` 파이프라인 재실행으로 자동 갱신 (수기 편집 금지).

## 구현 단계
1. `app/schemas/observability.py`에 4개 응답 Pydantic 모델 정의. 빈 데이터 케이스를 대비해 모든 집계 필드는 기본값(0 또는 빈 리스트)을 갖도록 설계.
2. `app/services/observability_service.py`에 `ObservabilityService(db)` 클래스 작성:
   - `summary()`: `projects.status` GROUP BY COUNT, `intake_requests.status`/`tickets_status` GROUP BY COUNT, `pipeline_run_events`를 `run_id`로 묶어 최근 N일(`occurred_at`/`created_at` 기준) outcome 집계(성공/실패율), `delivery_events` 최신 N건(`created_at DESC LIMIT`).
   - `usage(from_, to, group_by: Literal["project_id","seat_id","model","request_kind"], task_id: str | None)`: `llm_usage_ledger`를 기간 필터 + 단일 축 GROUP BY, `SUM(input_tokens)`/`SUM(output_tokens)`/`SUM(cost)`/`COUNT(*)`. `task_id` 지정 시 프로젝트 상세 드릴다운(해당 task_id로 추가 필터).
3. `runs`/`runs/{issue_key}`는 기존 `PipelineRunService`를 그대로 호출하는 얇은 라우트 함수로 구현 (신규 집계 로직 없음). 응답에 `intended_model != actual_model` 플래그가 기존 서비스 출력에 없다면, 서비스 레이어에 한 필드만 국소 추가(신규 마이그레이션 없이 `data` JSONB에서 파생).
4. `seats`는 `SeatQuotaService.latest()`가 반환하는 계정×window×scope 행을 `user_anthropic_credentials` 조인(계정→시트 상태) + 시트별 최근 24h `llm_usage_ledger` SUM으로 감싸는 신규 메서드 추가.
5. `app/api/v1/observability.py`에 4개 GET 라우트 작성. 형제 라우터(`llm_ledger.py`)와 동일하게 라우터 레벨 `dependencies=[Depends(require_permission("settings:manage"))]` 적용, `db: AsyncSession = Depends(get_db)` 주입.
6. `app/api/v1/router.py`에 import + `include_router(observability_router)` 1줄씩 추가.
7. 빈 데이터 방어: 각 서비스 메서드가 결과 0건이어도 예외 없이 기본 구조(0/빈 리스트) 반환하는지 확인 — GROUP BY 결과가 없는 조합은 SQL이 아니라 스키마 기본값으로 채움.
8. `clickeye-api/scripts/export_openapi.py` 실행 → `clickeye-contracts/openapi/openapi.json` 갱신 → `clickeye-contracts/scripts/generate-ts.sh`(또는 `pipeline.sh`)로 `generated/typescript/*.gen.ts` 재생성.

- 커버리지 ≥70% (신규 파일 기준).

## 준수할 컨벤션
- 커밋 메시지: `[api] CE-388 ...` (한국어).
- 라우터 등록은 `router.py`의 기존 `from app.api.v1.<module> import router as <x>_router` + `api_v1_router.include_router(<x>_router)` 2줄 패턴 그대로.
- 관리자 가드는 `require_permission("settings:manage")` 형제 패턴 준수(신규 permission 문자열 추가 금지).
- Contract 우선 원칙: 엔드포인트 구현 완료 후 반드시 `openapi.json` + 생성 TS 타입 동기화까지 포함(코드 변경만 하고 contracts 미동기화 상태로 끝내지 않음).
- 신규 마이그레이션 0 — 모든 쿼리는 기존 테이블/컬럼만 사용.

## 도메인 제약 (Domain Constraints)
- **정합성 규칙**: `runs`의 run 단위 그룹핑은 `pipeline_run_events.run_id`가 유일한 그룹 키이며 별도 `pipeline_runs` 테이블은 존재하지 않는다 — 서비스 레이어에서 GROUP BY로 파생해야 하며, 이 특성은 CE-388에만 국한되지 않고 파이프라인 관측 전반에 계속 참인 제약이다.
- **금지 사항**: `seat_quota_snapshots`/`llm_usage_ledger`는 운영 스냅샷·집계 데이터로 간주되어(CE-387 판단 근거: "PII 아님") governance-token이 아닌 RBAC(`settings:manage`) 가드로 노출하되, 원본 계정 인증정보(`encrypted_api_key` 등)는 어떤 관측 엔드포인트 응답에도 포함해서는 안 된다.
