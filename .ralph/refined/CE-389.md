## 목표
`(dashboard)/layout.tsx`에 "관측" nav 그룹과 대시보드 홈(`/dashboard`)을 신설하고, CE-388 관측 API(`/observability/summary|usage|runs|seats`)를 소비하는 4개 화면(대시보드 홈·토큰/시트·사용량 원장·실행 이력)과 기존 `/admin/intake` 인라인 확장에 원천 데이터 드릴다운을 추가한다.

## 가정 (Assumptions)
- **차트 라이브러리 미설치**: `recharts`/`tremor`/`visx` 없음. 신규 의존성 도입은 범위 확장이므로, 파이프라인 성공률 추이·게이지·피벗 표는 기존 관례(수기 `<table>`/`<div>` + Tailwind)로 구현한다. 시각적 트렌드가 필요한 곳(파이프라인 성공률 추이)은 막대/도넛을 CSS(`width: %`, `conic-gradient`) 로 대체한다. (근거: 기존 코드베이스에 차트 lib 부재 확인, 새 패키지 추가는 YAGNI 위반 소지)
- **데이터 페칭 패턴**: 서버 컴포넌트 fetch 대신, 기존 `/admin/intake` 패턴(TanStack Query + `hooks/use-*.ts` + `lib/api-client.ts`)을 그대로 따른다. (근거: 이미 확립된 컨벤션, admin/intake가 유일한 실측 데이터 소비 템플릿)
- **`apiClient.observability` 신규 추가**: contracts 레포에 observability 타입이 없어 hey-api 생성 대상이 아니므로, `lib/api-client.ts`에 손으로 `observability.getSummary/getUsage/getRuns/getSeats` 메서드를 추가한다. contracts 우선 원칙과 충돌하지 않는지 확인 필요 — CE-388이 contracts 동기화를 이미 완료했다고 알려져 있으므로(관련 커밋 `aecf0ee`), **contracts 레포에 타입이 실제로 없는지 재확인 필요**. 없다면 이 스펙은 clickeye-api 스키마(snake_case) 기준으로 웹 타입을 손으로 정의한다.
- **인테이크 원천 데이터 뷰는 별도 라우트가 아니라 기존 인라인 확장 패턴 확장**: `/admin/intake`에 `[id]` 서브라우트를 새로 만들지 않고, 기존 `expanded` 인라인 `<tr>` 확장 영역에 `payload` JSON 뷰어 섹션 + 티켓 원장(Linear 링크) 섹션을 추가한다. (근거: 티켓의 "신규 메뉴가 아니라 기존 인테이크 메뉴의 드릴다운" 명시, 기존 코드에 이미 `IntakeTimeline`/`refined_text` 표시가 있어 확장이 신규 라우트보다 작은 변경)
- **`payload` 원본 JSON 필드 존재 여부 미확인**: intake 스키마에 원본 `payload`(raw JSON) 필드가 실제로 존재하는지 코드에서 직접 확인하지 못했다. 구현 착수 시 `clickeye-api/app/schemas/intake*.py` 또는 관련 모델을 먼저 확인하고, 필드가 없으면 이 부분만 스코프에서 제외하고 보고한다(발견물로 기록, 임의로 필드를 만들지 않음).
- **RBAC**: 관측 메뉴는 기존 `adminItems`/`opsItems`와 동일하게 RBAC 불리언으로 게이팅한다고 가정(`showOps` 재사용). 별도 권한 신설은 금지범위 밖(계정 선택 자동화 금지와는 무관)이나, 명시 근거 없어 가장 보수적으로 기존 `showOps` 플래그를 그대로 재사용한다.

## 대상 파일
- `clickeye-web/src/app/(dashboard)/layout.tsx` — `observabilityItems: NavItem[]` 배열 추가(대시보드 홈 링크는 top-level `navItems`에, 토큰/시트·사용량 원장·실행 이력은 새 섹션에), `t("sections.observability")` 헤더, `showOps` 게이팅 재사용, 아이콘은 기존 미사용 `BarChart3`(lucide-react) 등 재사용
- `clickeye-web/src/lib/api-client.ts` — `observability.getSummary()/getUsage(params)/getRuns(params)/getRunDetail(issueKey)/getSeats()` 메서드 추가 (기존 `request<T>()` 패턴 재사용)
- `clickeye-web/src/lib/api-types/observability.ts` — 신규. `clickeye-api/app/schemas/observability.py`, `seat_quota.py`, `pipeline_run.py` 필드명을 그대로 옮긴 TS 인터페이스(camelCase 변환 없이 API 응답 그대로, 이미 alias 처리되어 있다면 그 형태 유지)
- `clickeye-web/src/hooks/use-observability.ts` — 신규. `useObservabilitySummary()`, `useUsagePivot(filters)`, `useRunsList(filters)`, `useRunDetail(issueKey)`, `useSeats()` — 기존 `use-intake.ts` 패턴(query key 배열, `retry:false`, `enabled:!!token`, `isFeatureDisabled` 404 처리) 그대로 재사용
- `clickeye-web/src/app/(dashboard)/dashboard/page.tsx` — 신규. 위젯 그리드(상태/진행률/완성률 카드, 인테이크 깔때기, 파이프라인 성공률 추이, 최근 딜리버리 피드) — `/observability/summary` 소비
- `clickeye-web/src/app/(dashboard)/observability/seats/page.tsx` — 신규. 계정별 잔량 게이지·리셋 카운트다운·소진 예측/페이스 배지·시트 상태·24h 소비·스냅샷 신선도
- `clickeye-web/src/app/(dashboard)/observability/usage/page.tsx` — 신규. 프로젝트×시트×모델 피벗 테이블, 기간 필터, 합계, `task_id` 클릭 시 실행 이력 드릴다운으로 이동(query param 전달)
- `clickeye-web/src/app/(dashboard)/observability/runs/page.tsx` — 신규. run 목록(티켓 키·outcome·소요·모델 불일치 경보) + 상세 타임라인(단계 이벤트)은 동일 페이지 내 선택 패널 또는 `?issue=` 쿼리로 상세 표시(신규 라우트 `[issueKey]` 대신 페이지 내 상태 전환, admin/intake와 동일한 "인라인 확장" 관례 유지)
- `clickeye-web/src/app/(dashboard)/admin/intake/page.tsx` — 수정. 기존 `expanded` 인라인 영역에 원본 `payload` JSON 뷰어(접기/펼치기) + 발급 티켓 원장(Linear 링크) 섹션 추가. **기존 레이아웃/탭/컴포넌트 구조 변경 금지, 섹션 추가만.**
- `clickeye-web/src/components/observability/*.tsx` — 신규 공용 컴포넌트(필요 시): 게이지/카운트다운/피벗 테이블 셀 등. 페이지별 1회성 UI는 컴포넌트 분리 없이 페이지 파일에 직접 작성(YAGNI, 조기 추상화 금지)
- `clickeye-web/messages/{ko,en}.json` 또는 해당 i18n 리소스 — `sections.observability`, 각 페이지 라벨 키 추가 (기존 i18n 구조 그대로)

## 구현 단계
1. `clickeye-api/app/schemas/observability.py`, `seat_quota.py`, `pipeline_run.py`를 읽고 실제 응답 필드를 확정 → `lib/api-types/observability.ts` 작성
2. intake 관련 스키마/모델을 확인해 `payload`(원본 JSON) 필드 실존 여부 확정. 없으면 그 사실을 보고하고 해당 섹션만 스코프 제외
3. `lib/api-client.ts`에 `observability` 네임스페이스 메서드 추가 (기존 `request<T>()` 재사용, 신규 fetch 로직 작성 금지)
4. `hooks/use-observability.ts` 작성 — `use-intake.ts`의 로딩/에러/피처비활성(404) 처리 패턴을 그대로 복제
5. `dashboard/page.tsx` 작성 — summary 응답의 `projects_by_status`/`intake_by_status`/`pipeline_run_success_rate`/`recent_delivery_events`를 각 위젯에 매핑, 빈 상태는 intake 페이지와 동일한 muted-text 컨벤션
6. `observability/seats/page.tsx` 작성 — `SeatObservabilityEntry.windows[]`(5h/7d 등 `window`+`scope_name` 별)를 게이지로, `projected_exhaustion_at`/`ahead_of_pace` 배지, `usage_fetched_at` 기준 "n분 전 갱신" 신선도 표시
7. `observability/usage/page.tsx` 작성 — `UsagePivotResponse.buckets`를 group_by(프로젝트×시트×모델) 축으로 피벗, 기간 필터는 쿼리 파라미터로 훅에 전달, `task_id` 클릭 시 `router.push('/observability/runs?task_id=...')`
8. `observability/runs/page.tsx` 작성 — 목록은 `PipelineRunResponse[]`, 행 클릭 시 `useRunDetail(issueKey)`로 상세 이벤트 스레드를 같은 페이지 하단/사이드 패널에 표시(신규 라우트 추가하지 않음)
9. `(dashboard)/layout.tsx`에 nav 배열·i18n 키 추가 (배열 추가 외 기존 nav 로직 변경 금지)
10. `admin/intake/page.tsx`의 `expanded` 블록에 `payload` JSON 뷰어(단계 2 결과에 따라 조건부)와 티켓 원장(Linear 링크, `tickets` 테이블 연계 — API에 해당 필드/엔드포인트가 없으면 신규 백엔드 필요로 판단해 스코프 제외하고 보고) 섹션 삽입
11. 각 페이지에 다크모드(`dark:`)·반응형(375/768/1280)·빈 상태 디자인 적용, lint/typecheck/build 실행

## 테스트
- 신규 훅(`use-observability.ts`)에 대해 기존 `use-intake.ts` 테스트 패턴을 참고한 단위 테스트(성공/에러/빈 응답/404-feature-disabled 케이스) — 커버리지 ≥70%
- 신규 페이지는 최소 렌더 스모크 테스트(로딩→데이터→빈 상태 3케이스) — 기존 admin/intake 테스트 존재 시 그 구조 그대로 복제
- `pnpm lint && pnpm typecheck && pnpm build` (또는 레포의 실제 스크립트명 확인 후) 통과 확인
- 실데이터 렌더 확인: 로컬에서 clickeye-api 기동 후 5개 화면 모두 목 데이터 없이 응답 확인(수용 기준 "목 데이터 금지" 직접 검증)

**발견물(작업 목표와 무관, 별도 처리 대상)**
- `/admin/intake`에 상세 라우트가 없어 "원형으로 계보 추적" 요구가 인라인 확장만으로는 정보 밀도상 부족할 수 있음 — 필요 시 별도 `[id]` 라우트 도입은 T4(구조 변경)로 사용자 승인 필요
