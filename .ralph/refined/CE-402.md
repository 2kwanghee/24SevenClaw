## 목표
`observability_service.py`의 `summary()`/`usage()`를 하드코딩된 7일 윈도우 제거·기간 파라미터화하고, 일자별 성공률 추이(`daily_outcomes`)와 프로젝트 상세 집계 신규 엔드포인트를 추가해 대시보드 D2가 필요로 하는 관측 데이터를 제공한다.

## 가정 (Assumptions)
- `seats` 응답은 프로젝트당 seat 수가 적다고 가정하고 페이지네이션 없이 전체 반환한다(기존 `/summary`·`/usage`도 비페이지네이션). seat 수가 많아질 근거가 태스크에 없어 보수적으로 무제한 처리하되, 과도하면 후속 티켓으로 분리.
- `daily_outcomes`의 `success`/`failure` 판정은 기존 `_SUCCESS_OUTCOMES`/`_FAILURE_OUTCOMES` 세트(demoted/unknown 제외)를 그대로 재사용한다 — 새 분류 기준을 만들지 않음.
- `trend_days`(1~14)가 `days`(1~90)보다 클 수 있으므로, `trend_days > days`인 경우 `min(trend_days, days)`로 캡한다(스펙에 명시 없어 보수적 선택 — 존재하지 않는 기간의 추이를 만들지 않기 위함).
- 빈 데이터에서도 `daily_outcomes` 날짜 슬롯을 채워야 하므로(수용 기준), `trend_days`만큼의 연속 날짜 리스트를 먼저 생성한 뒤 실제 카운트를 매핑한다(0/0으로 채움).
- `GET /observability/projects/{project_id}/summary`도 라우터 레벨 가드(`require_permission("settings:manage")`)를 그대로 상속받는다 — 별도 권한 체계를 새로 만들지 않음.
- `project_id`가 존재하지 않는 프로젝트여도 500 대신 빈 집계(0/None/빈 리스트) 200을 반환한다 — 기존 "no 500 on empty data" 컨벤션 준수(`observability.py` 모듈 docstring).
- ledger의 `seat_id`가 NULL인 행은 `seat_id: null, account_email: null`로 별도 그룹 없이 하나의 버킷에 합산한다(태스크 명시사항).

## 구현 단계
1. `observability_service.py`: `summary(db, days=7, trend_days=3)`로 시그니처 변경, `since = now - timedelta(days=days)`로 대체하고 `_RECENT_DAYS` 하드코딩 참조 제거.
2. `_daily_run_outcomes(db, since, trend_days)` 신규 구현 — capped `effective_trend_days = min(trend_days, days)` 기준으로 오늘 포함 연속 날짜 리스트 생성 후, `PipelineRunEvent`를 `date(created_at)`로 groupby하여 `_SUCCESS_OUTCOMES`/`_FAILURE_OUTCOMES` 기준으로 success/failure 카운트, 날짜 슬롯에 매핑(누락 날짜는 0/0).
3. `summary()` 반환 dict에 `daily_outcomes` 키 추가, 나머지 기존 필드(`pipeline_run_success_rate` 등)는 무변경 로직 유지(days=7 미지정 시 기존과 동일 응답 보장).
4. `usage()` 시그니처에 `project_id: str | None = None` 추가, 기존 `task_id` 필터(line 97-102)와 동일한 패턴으로 `LlmUsageLedger.project_id == project_id` 조건 조건부 추가.
5. `project_summary(db, project_id)` 신규 구현 — `LlmUsageLedger`를 `project_id`로 필터해 `SUM(input_tokens)`, `SUM(output_tokens)`, `SUM(cost)` 집계, `seat_id`(nullable)로 groupby하여 seat별 토큰 합산 후 `UserAnthropicCredential` 또는 연결된 계정 테이블과 조인해 `account_email` 채움(seat_id NULL 그룹은 email NULL), `first_activity_at`/`last_activity_at`는 ledger와 `pipeline_run_events`(둘 다 `project_id` 인덱스 보유) 각각의 `MIN(created_at)`/`MAX(created_at)`을 구해 전체 min/max로 병합.
6. `observability.py` 라우터: `/summary`, `/usage` 쿼리 파라미터 추가 후 서비스 함수 호출부에 그대로 전달. 신규 `GET /projects/{project_id}/summary` 라우트 추가(라우터 prefix 상속으로 권한 가드 자동 적용).
7. `schemas/observability.py`: `DailyOutcome`, `ProjectSummaryResponse`, `ProjectSeatUsage` 신규 Pydantic 모델 추가, `ObservabilitySummaryResponse`에 `daily_outcomes` 필드 추가(기존 필드는 건드리지 않음 — 필드 제거/개명 금지).
8. `openapi_export.py` 실행하여 `clickeye-contracts/openapi/openapi.json` 갱신, 이어서 TS 타입 재생성 커맨드 실행(수동 편집 금지, 커맨드는 api-agent.md/contracts-agent.md 참조).
9. `tests/test_observability.py`: `_seed_pipeline_run_event(db_session, project_id, event, outcome, created_at)`, `_seed_ledger_row(db_session, project_id, seat_id, input_tokens, output_tokens, cost, created_at)` 헬퍼 추가.
10. 테스트 작성 — `/summary`: `days=30` 다른 응답 검증, `days` 생략 시 기존과 동일 응답(무회귀), `daily_outcomes` 빈 데이터에서도 날짜 슬롯 채워짐 200. `/usage`: `project_id` 필터 적용 검증, 기존 `task_id` 필터 회귀 없음, 잘못된 값 422. `/projects/{project_id}/summary`: 실데이터 토큰 합/기간이 ledger 원본과 일치, seat_id NULL 행 email NULL로 포함, 존재하지 않는 project_id는 빈 집계 200(500 아님).

## 준수할 컨벤션
- Contract 우선: openapi.json 먼저 갱신 → `clickeye-contracts/generated/` 재생성, 수동 편집 금지(governance gate가 contract-drift 검사로 차단).

- async-only DB 호출, `*` import 금지, 하드코딩 설정값 금지(`_RECENT_DAYS` 제거가 이 원칙의 일부).
- 새 Pydantic 모델은 기존 응답 필드 제거/개명 없이 추가만 — 하위호환 유지.
- 브랜치명에 Linear 키(`CE-402`) 포함, 커밋 메시지 한국어 `[api] ...` 형식.
- 마이그레이션 미발생 확인 시 자동생성 diff에서 불필요한 `drop_table`/`drop_index` 없는지 검토(CE-370 재발 방지 컨벤션) — 이번 작업은 마이그레이션 자체가 없어야 함.
