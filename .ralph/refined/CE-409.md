## 목표
`AUTO_MERGE` 직접 머지 경로(`scripts/auto_dev_pipeline.sh:1531-1620`)에서 `git push origin main` 실패를 `RUN_OUTCOME=merged`로 위장 처리하던 결함을 fail-closed로 고쳐, push 실패 시 PR 폴백으로 강등하고 "머지 성공" 로그는 원격 반영이 실증된 뒤에만 남긴다.

## 가정 (Assumptions)
- 재시도는 `git pull --no-rebase` 1회로 한정한다 (수용 기준에 "재시도 정책 일반은 금지범위"로 명시돼 있어, 무한/다회 재시도 정책 설계는 하지 않고 요청된 "1회"만 구현).
- reconcile 브랜치명은 요청대로 `fix/<KEY>-reconcile` 고정 포맷을 사용한다(기존 CE-405 사례에서 오케스트레이터가 수동으로 쓴 것과 동일 관례).
- `auto_pr_creator.py`는 `--branch`만 받고 별도 diff-base 인자가 없으므로, reconcile 브랜치를 그대로 `--branch` 인자로 넘겨 기존 PR 생성 경로를 재사용한다(신규 CLI 옵션 추가 안 함).
- 재시도용 `git pull --no-rebase`가 다시 충돌하면 즉시 `git merge --abort`(pull 내부) 실패로 이어질 수 있으므로, 이 경우도 "재시도 실패"로 간주해 PR 폴백으로 간다(보수적 선택 — 무인 배치에서 충돌 자동 해소를 시도하지 않음).
- `git ls-remote origin main` 출력의 SHA가 로컬 머지 커밋 SHA(`git rev-parse main`)와 일치하는지로 "원격 반영 실증"을 판정한다(merge-base 실증과 동일하게 새 외부 의존 없이 기존 git 명령만 사용).

## 대상 파일
- `scripts/auto_dev_pipeline.sh:1590-1596` — push 성공 확인 로직으로 교체 (기존 `safe_git push origin main 2>/dev/null || log "WARN: push 실패"` 한 줄 + 브랜치 정리 두 줄을 대체). 브랜치 삭제(`branch -d`, `push --delete`)는 push 성공 확인 이후로 이동.
- `scripts/auto_dev_pipeline.sh:1554-1556` — "머지 성공" 로그 및 `RUN_OUTCOME="merged"` 설정 위치를 push 성공 실증 이후로 이동(현재는 로컬 merge 직후 찍혀 push 실패와 무관하게 이미 성공 로그가 남음).
- `scripts/tests/test_workspace_delivery.sh` — 기존 정상 push 경로 테스트가 있다면 회귀 확인용으로 실행(신규 케이스 추가 대상 아님, 무회귀 확인 목적). 신규 테스트는 아래 신규 파일에 작성.
- `scripts/tests/test_direct_merge_push_fallback.sh` (신규) — 비-FF push 거부 시나리오(로컬에 원격보다 뒤처진 fake origin을 만들어 `git push`가 실패하도록 구성) → PR 폴백 발동 검증. 기존 `scripts/tests/test_*.sh` 스타일(예: `test_intake_branch.sh`) 참고해 동일한 mock/구조 사용.

## 구현 단계
1. `scripts/auto_dev_pipeline.sh:1552-1556`의 `elif safe_git merge ... && safe_git merge-base --is-ancestor ...` 성공 분기에서, 기존처럼 로컬 merge-base 실증까지는 유지하되 `RUN_OUTCOME="merged"` 확정과 "머지 성공" 로그 출력을 **뒤로 미루고**, 우선 `MERGED_DIRECT=true`만 세팅한 뒤 머지 로그 파일 생성(1558-1588, 변경 없음) 단계로 진행한다.
2. 머지 로그 생성 직후(현재 1591번째 줄 위치)에 push 확인 블록을 추가한다:
   - `safe_git push origin main`을 시도. 성공하면 `git ls-remote origin main`의 SHA를 로컬 `git rev-parse main`과 비교해 일치할 때만 "머지 성공: ... (원격 반영 실증)" 로그 + `RUN_OUTCOME="merged"` 확정.
   - 실패(또는 ls-remote SHA 불일치)하면 `git pull --no-rebase origin main` 1회 시도 → 성공 시 재-`git push origin main` → 성공하면 위와 동일하게 `ls-remote` 재확인 후 성공 처리.
   - 재시도(pull 또는 재-push)도 실패하면 3단계(reconcile 폴백)로 진입.
3. reconcile 폴백: 로컬 main(머지 커밋 포함 HEAD)을 `git push origin main:refs/heads/fix/${ISSUE_KEY}-reconcile` 형태로 새 브랜치에 push. 성공하면 `python3 scripts/auto_pr_creator.py --branch "fix/${ISSUE_KEY}-reconcile"` 호출로 PR 생성, `RUN_OUTCOME="pr"`로 강등, `MERGED_DIRECT=false`로 되돌린다. 이후 로컬 main을 `git fetch origin && git reset --hard origin/main`으로 재정렬한다.
4. 브랜치 정리(`branch -d "$BRANCH"`, `push origin --delete "$BRANCH"`, 현재 1594-1595)는 2단계에서 push 성공(원격 반영 실증 포함)이 확정된 경로로만 이동시킨다. reconcile 폴백 경로에서는 원본 `$BRANCH`를 삭제하지 않는다(원격 미반영 상태에서 작업 브랜치까지 지우면 산출물이 완전히 유실되므로).
5. LLM 인제스트 블록(1597-1611)은 push 성공 확정 경로 안쪽 그대로 유지(순서상 push 확인 로직 뒤에 위치하게 됨).
6. 신규 테스트 `scripts/tests/test_direct_merge_push_fallback.sh` 작성: bare 원격 저장소를 만들고 원격 main을 로컬보다 먼저 전진시킨 뒤 파이프라인의 해당 로직(또는 이를 함수로 뽑은 형태)을 실행해 `RUN_OUTCOME=pr`이 나오는지, `fix/<KEY>-reconcile` 브랜치가 원격에 존재하는지, 원본 브랜치가 삭제되지 않았는지를 assert한다.

## 테스트
- 신규: `scripts/tests/test_direct_merge_push_fallback.sh` — 비-FF 거부 시뮬레이션(원격이 로컬보다 앞선 상태 재현) → PR 폴백 경로(`RUN_OUTCOME=pr`, reconcile 브랜치 존재, `auto_pr_creator.py --branch fix/<KEY>-reconcile` 호출) 검증.

- 원격 반영 실증: 정상 push 경로 테스트에서 `git ls-remote origin main`의 SHA가 로컬 머지 커밋과 일치함을 확인하는 assertion 추가.

## 도메인 제약 (Domain Constraints)
- **정합성 규칙**: "머지 성공" 로그·`RUN_OUTCOME=merged`는 로컬 merge-base 실증만으로 확정해서는 안 되며, `git ls-remote`로 원격 HEAD가 실제로 머지 커밋을 포함함을 확인한 뒤에만 확정한다(이번 결함의 재발 방지 핵심 불변식 — CE-393의 merge-base 실증 원칙을 원격까지 확장).
- **금지 사항**: push 실패(비-FF 포함)를 `|| log "WARN"`으로 삼켜 성공 처리하지 않는다. 브랜치 삭제(`branch -d`, `push --delete`)는 원격 push 성공 확인 이전에 수행하지 않는다.
